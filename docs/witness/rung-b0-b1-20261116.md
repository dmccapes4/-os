## What exists

`kernel/` in the `-os` repo:

| File | What it is |
|---|---|
| `src/boot.S` | The assembly only assembly can do: park cores 1–3, drop EL3→EL2→EL1 as needed, set the stack below the image, zero BSS, jump to C. |
| `src/kernel.c` | `kernel_main`: firmware mailbox → 1024×768 framebuffer → draws `HELLO-KYRIOS` plus two witness lines in a hand-set 5×7 glyph set (a real font/console is B4). No libc, no Linux syscalls — there is no one to call. |
| `src/link.ld` | Loads at `0x80000`, the Pi 4 `kernel8.img` address. |
| `Makefile` | `aarch64-linux-gnu-gcc -ffreestanding -nostdlib`, objcopy to `kernel8.img`. |
| `extract_firmware.py` | Read-only FAT32 parser that pulls `start4.elf`, `fixup4.dat`, and the BCM2711 DTBs out of the checksum-verified official Pi OS image (found the DTBs behind long filenames; LFN support added and noted). |
| `boot-sd/` | The boot payload: firmware blobs (gitignored, re-extractable), `config.txt` (`kernel=kernel8.img`, `arm_64bit=1`), and our `kernel8.img`. |
| `stage_boot_sd.sh` | Operator-run: copies the payload onto a mounted spare card's boot partition and prints the booting kernel's SHA-256. |

## B1 — what remains, and exactly how it passes

1. You stage a **spare** SD (not `valseir`'s working Pi OS card):
   mount its FAT boot partition anywhere on this bench, then
   `./kernel/stage_boot_sd.sh /path/to/mount`.
2. Card into `valseir`, its screen attached (it has one — that is partly
   why it drew first shift), power on.
3. **Pass:** the screen shows `HELLO-KYRIOS` on a deep slate field, with
   the two smaller witness lines beneath. A photo of that screen, filed
   here, is B1's receipt. No photo, no pass — a kernel that cannot show
   itself has not booted for our purposes.
4. If the screen stays dark or rainbow: that is data too — photograph
   whatever it *does* show (the firmware's rainbow/4-blinks codes are a
   witness), and the fault gets named before anything is re-flashed.

Known risks, written before the fact so the test can convict them:
mailbox buffer addressing (the tutorial-standard low-memory form is used),
EL at entry (EL3 and EL2 entries are both handled), and `bootcode.bin`
being unnecessary on Pi 4 (EEPROM boots; the file rides along harmlessly).
